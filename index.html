1Problem statement

Design an iterator over a BST, initially positioned before the smallest element. The constructor gets the root.

next() moves to the next element and returns it · prev() moves to the previous element and returns it · hasNext() / hasPrev() say whether such an element exists.

For inorder [1, 3, 5, 7, 15] the start is [-1] [1] [3] [5] [7] [15], where -1 is the position before the first element. Example: next→1, next→3, next→5, prev→3, next→5, next→7.

    3Let's solve it without knowing the solution

    “Suppose interview mein ye question aa gaya, aur tumne ise kabhi solve nahi kiya. Toh kaise approach karoge?”

    We need a class that can iterate over a BST — a pointer that can move forward and backward.

    Observation 1 — We need a fixed orderIf I need next() and prev(), “next of what?” needs an answer. I need the elements in some fixed order so “one step right/left” means something.
    Observation 2 — BST gives us inorderThe moment I see a BST, one traversal comes to mind: inorder (Left → Root → Right). Watch it happen:
    Observation 3 — Inorder gives sorted orderEverything on the left is smaller than the root, everything on the right is larger. So Left → Root → Right always emits values in ascending order.
    BST→Inorder→Sorted order→next / prev = step right / left
    Observation 4 — Pointer starts before the first elementThe pointer is not on an actual element yet. The first element has index 0, so “before it” is index -1.

    4Straightforward solution

    Now that sorted order exists, the simplest thing is to store it: vector<int> inorder for the sequence and int index = -1 for the pointer. Then next(): index++, return inorder[index] and prev(): index--, return inorder[index].

    -1 is only the initial position. prev() never sets the index to -1 on its own: it is only legal while hasPrev() is true (index > 0).

    6Complexity

    Construction: time O(N), extra space O(N) (the whole inorder vector). Each next(), prev(), hasNext(), hasPrev(): O(1) time. The O(N) cost is paid once, up front — not per operation.

    7But wait… do I really need to store everything?

    What do I actually need to get the next element? Not every value — just enough to know where to go next in the tree.

    Inorder goes as far left as possible before visiting: 7 → 3 → 1. Those nodes are exactly the ancestors still waiting for me. That is a stack.

    Careful: the textbook stack iterator is forward-onlyThe usual version pops a node to return it. Once popped, the way back is lost, so prev() cannot work. Correctness beats forcing a stack-only trick.
    The fix: keep the path, don't pop itKeep the root-to-current path in a stack-like vector; the top is the current node. next() = inorder successor, prev() = inorder predecessor, both found using only that path.
    • has right child → go right once, then as far left as possible (push)
    • otherwise → pop until we arrive from a left child (that parent is the answer). prev() is the mirror image. Empty path = before the first element.

    10Complexity comparison

    Array approachPath-stack approach
    PreprocessingO(N) timenone (constructor stores root)
    Extra spaceO(N)O(H): O(log N) balanced, O(N) skewed
    next() / prev()O(1)O(H) worst case; amortized O(1) when walking one direction through the whole tree
    hasNext() / hasPrev()O(1)O(H) (scans the path)

    Honest trade-off: alternating next()/prev() across a deep boundary can cost O(H) every call, so there is no blanket amortized O(1) here. You save space and preprocessing, not constant-time guarantees. Calling next()/prev() only when the matching has…() is true is assumed.

    11Final intuition

    BST→need an order→inorder→sorted→pointer before first→next = right · prev = left

    The important part wasn't memorizing the code. It was noticing: BST → Inorder → Sorted Order → Iterator — and then asking whether storing the whole order was necessary.
